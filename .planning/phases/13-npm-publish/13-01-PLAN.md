Create `.github/workflows/` directory and `.github/workflows/release.yml` with two jobs.

Per D-03, trigger on tag push only with pattern `v*`:
```yaml
on:
  push:
    tags:
      - 'v*'
```

**Job 1: `publish`** (runs on `ubuntu-latest`):
1. `actions/checkout@v4`
2. `pnpm/action-setup@v4` with `version: 10`
3. `actions/setup-node@v4` with `node-version: '22'`, `cache: 'pnpm'`, and CRITICALLY `registry-url: 'https://registry.npmjs.org'` (without this, NODE_AUTH_TOKEN is ignored and publish fails with ENEEDAUTH)
4. `pnpm install --frozen-lockfile` (from repo root -- lockfile is at root)
5. `pnpm --filter twentythree-cli test --run` (run existing test suite)
6. `pnpm --filter twentythree-cli run build` (tsdown + oclif manifest via postbuild)
7. Publish step with `working-directory: packages/twentythree-cli`, command `pnpm publish --no-git-checks --access public`, env `NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}`. The `--no-git-checks` flag is required because GitHub Actions checks out in detached HEAD state. The `--access public` flag is required on first publish for unscoped packages. Per D-07, auth uses classic automation token stored as `NPM_TOKEN` repository secret.

**Job 2: `smoke-test`** (runs on `ubuntu-latest`, `needs: publish`):
1. `actions/setup-node@v4` with `node-version: '22'` (no registry-url needed, no repo checkout needed)
2. Registry propagation polling: loop 5 times with 15s sleep, running `npm view twentythree-cli@${GITHUB_REF_NAME#v} version 2>/dev/null && break`. The `${GITHUB_REF_NAME#v}` strips the `v` prefix from tag name dynamically so the workflow works for all future releases.
3. `npm install -g twentythree-cli` (per D-02, smoke test installs from npm in a clean environment)
4. `twentythree --version` (must exit 0)

Per D-07, the `NODE_AUTH_TOKEN` env var is scoped ONLY to the publish step (not job-level) to avoid token exposure in other step logs.

The workflow name should be `Release`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → npm registry | CI runner authenticates to npm using NPM_TOKEN secret to publish package |
| npm registry → end user | Published package is downloaded and executed globally by end users |
| GitHub repository secrets → workflow env | NPM_TOKEN secret injected into workflow environment variable |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-01 | Information Disclosure | release.yml publish step | mitigate | Scope `NODE_AUTH_TOKEN` env var to publish step only (not job-level); never echo token in any run step |
| T-13-02 | Elevation of Privilege | release.yml tag trigger | accept | Any user with push access can create tags and trigger publish; tag protection rules recommended but deferred to v1.2 |
| T-13-03 | Tampering | release.yml action versions | accept | Using `@v4` tags (not pinned to SHA); acceptable for v1.0 release, pin to SHA in v1.2 for supply chain hardening |
| T-13-04 | Information Disclosure | npm package contents | mitigate | `files` array in package.json already whitelists only `/bin`, `/dist`, `/oclif.manifest.json`, `/docs`, `/README.md` — no source code, tests, or config files leak into tarball |
</threat_model>
