# Phase 9: Endpoint Coverage Audit - Context

**Gathered:** 2026-04-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Audit all 235 OpenAPI endpoints against the 254 command files (215 unique `agentMetadata.api_endpoint` values). For every endpoint: either a command covers it, or a rationale entry exists in `EXCLUDED_OPERATIONS`. When both checks pass (no gaps, no phantoms), the audit script exits 0.

New capabilities (e.g. new resource groups, bulk operations) are out of scope — this phase closes coverage gaps only.

</domain>

<decisions>
## Implementation Decisions

### EXCLUDED_OPERATIONS Format

- **D-01:** Intentional omissions live as a TypeScript constant `EXCLUDED_OPERATIONS` in source (e.g. `src/lib/audit.ts`), co-located with the audit logic. Type-checked, importable by the audit script directly.
- **D-02:** Each entry has three fields: `endpoint` (e.g. `'POST /foo'`), `reason` (human-readable rationale string), and `category` (machine-groupable label, e.g. `'admin-only'`, `'internal'`, `'deprecated'`, `'super-admin'`).

### Gap Fill Quality Bar

- **D-03:** New commands for confirmed gaps must meet the full hand-authored quality standard — typed flags, `--json` output, table rendering, `static agentMetadata`, oclif conventions. Same bar as existing 219 commands. No skeletons.
- **D-04:** Endpoints that are truly admin/super-scope or have no practical CLI use case are excluded with rationale (added to `EXCLUDED_OPERATIONS`) rather than forced into a command. This keeps the CLI UX clean while the audit still exits 0.

### Phantom Detection

- **D-05:** The audit script checks BOTH directions:
  - Spec → commands: detect gaps (spec endpoints with no covering command and not excluded)
  - Commands → spec: detect phantoms (commands whose `api_endpoint` doesn't match any spec path)
- **D-06:** Phantoms cause the script to exit non-zero (same as gaps). A stale or mistyped `api_endpoint` is treated as an error, not a warning.

### Audit Script Design

- **D-07:** Script design (location, pnpm command name, output format) is left to Claude's discretion — follow the pattern of `update-api-spec.sh` for location and the pnpm scripts convention in `package.json` for the runner. Output should show a count of covered/uncovered/excluded/phantom endpoints and list any failures clearly.

### Claude's Discretion

- Script location, naming, and exact output format — follow existing patterns (`update-api-spec.sh` as a reference).
- Which `category` values to use in `EXCLUDED_OPERATIONS` — derive from the actual endpoints encountered (admin-only, super-admin, internal, deprecated are reasonable starting labels).
- The order of gap-fill vs script-writing within the plan — planner decides.

</decisions>

## Existing Code Insights

### Reusable Assets
- `packages/twentythree-cli/src/lib/output.ts` — `renderTable`, `formatJsonOutput`, `formatApiError`, `EXIT_ERROR` — used by all existing commands; new commands should import from here.
- `packages/twentythree-cli/src/lib/term-map.ts` — `applyCliTerms` — apply when rendering output that may contain legacy API terms (photo→video, album→category, live→webinar).
- `packages/twentythree-cli/update-api-spec.sh` — Reference for shell script conventions in this package.

### Established Patterns
- `static agentMetadata = { api_endpoint: 'METHOD /path', auth_scope, output_shape, side_effects }` — declared on every command class; the audit script reads these values.
- All commands: `static enableJsonFlag = true` + `--json` flag support.
- Commands extend `AuthenticatedCommand` (requires active workspace) or `BaseCommand` (no workspace needed).

### Integration Points
- `package.json` scripts — new `audit-endpoints` (or similar) pnpm script should be wired here.
- `oclif.manifest.json` — regenerated by `pnpm build`; the audit script should NOT depend on this (read source files directly for `api_endpoint` values).
