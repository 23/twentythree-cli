# Architecture Patterns

**Domain:** TypeScript/Node.js CLI for a large REST API surface (OpenAPI 3.1.0)
**Project:** twentythree — TwentyThree video platform CLI + AI skills package
**Researched:** 2026-04-14
**Overall confidence:** HIGH (stack choices verified against official docs and source code)

---

## Recommended Architecture

The system is a **pnpm monorepo** containing two independently-published npm packages:

1. `twentythree-cli` — the global CLI binary
2. `twentythree-skills` — the AI agent skills package

They share no runtime code. The skills package wraps the CLI via shell invocation; it is a collection of SKILL.md files and agent instruction documents, not a library.

## Component Boundaries

| Component | Responsibility | Communicates With | Notes |
|-----------|---------------|-------------------|-------|
| `commands/` | Parse CLI args, call API, format output | `api/client.ts`, `auth/store.ts` | One oclif Command class per file |
| `api/client.ts` | Typed HTTP wrapper around openapi-fetch | TwentyThree REST API | Stateless; accepts workspace URL + token |
| `api/auth-middleware.ts` | Signs every request with OAuth 1.0a | `api/client.ts` | Reads credentials from store on each call |
| `api/types.ts` | Generated TypeScript types from spec | (consumed by client.ts) | Regenerated via `generate-types.sh`; committed |
| `api/term-map.ts` | Translates modern CLI terms to legacy API params | `commands/` | e.g. "video" → "photo" in query params |
| `auth/store.ts` | Persists and retrieves credentials | OS keychain (keytar), fallback JSON file | Never holds tokens in memory longer than needed |
| `auth/workspace.ts` | Calls `/api/2/user/tokens?cross_sites_p=1`, presents workspace picker | `api/client.ts`, `auth/store.ts` | Runs once at `auth credentials`; result stored |
| `auth/token-refresh.ts` | Keeps tokens alive during long sessions | `auth/store.ts` | Polling interval; skips if no active session |
| `config/paths.ts` | Resolves `~/.config/twentythree/` via XDG spec | All modules that need FS paths | `xdg-basedir` package handles cross-platform |
| `skills/SKILL.md` | Agent instruction document for AI assistants | (read by agents at runtime) | References CLI commands by name; version-locked to CLI release |

## Data Flow

### Authentication Setup (one-time)

```
User runs: twentythree auth credentials
    |
    v
Prompts for domain + bearer token
    |
    v
auth/workspace.ts calls:
  GET {domain}/api/2/user/tokens?cross_sites_p=1
  (using supplied bearer token as initial OAuth credential)
    |
    v
Returns list of {site_id, domain, token} for all accessible workspaces
    |
    v
User selects default workspace (interactive prompt via @inquirer/prompts)
    |
    v
auth/store.ts writes to:
  - OS keychain via keytar (preferred) — each workspace stored as separate entry
  - Fallback: ~/.config/twentythree/credentials.json (encrypted-at-rest is OS responsibility)
    |
    v
config/paths.ts writes:
  ~/.config/twentythree/config.json  — { defaultWorkspace: "site_id" }
```

### Per-Command API Call

```
User runs: twentythree video list --limit 20
    |
    v
oclif routes to commands/video/list.ts
    |
    v
Command reads active workspace from config/paths.ts → config.json
    |
    v
auth/store.ts retrieves token for active workspace (keychain or JSON)
    |
    v
api/client.ts: createClient<paths>({ baseUrl: "https://{workspace.domain}/api/2" })
    |
    v
api/auth-middleware.ts onRequest():
  - Reads consumer key/secret + access token/secret for workspace
  - Computes OAuth 1.0a signature (oauth-1.0a library)
  - Injects Authorization header into request
    |
    v
openapi-fetch sends typed HTTP request to TwentyThree API
    |
    v
Response: { data, error, response }
    |
    v
api/term-map.ts: translates response field names (photo→video, album→category, live→webinar)
    |
    v
Command formats output:
  - Human: table/text via cli-table3 or formatted console.log
  - Agent: JSON envelope with { ok, data, summary, breadcrumbs } (mirrors Basecamp pattern)
```

### Token Refresh (background)

```
auth/token-refresh.ts starts interval on CLI startup
    |
    v
Every N minutes: check token expiry field for each active workspace
    |
    v
If approaching expiry:
  POST /api/2/session/token/refresh  (or equivalent endpoint)
    |
    v
auth/store.ts updates stored token (atomic write)
```

## Patterns to Follow

### Pattern 1: oclif Topic + Command Per File

**What:** Each API resource becomes an oclif topic (directory). Each operation becomes a command file. `video/list.ts` → `twentythree video list`.

**When:** Always. This is the oclif standard and is required for its manifest-based lazy loading.

**Example structure:**
```
src/commands/video/list.ts     → twentythree video list
src/commands/video/get.ts      → twentythree video get
src/commands/video/upload.ts   → twentythree video upload
src/commands/category/list.ts  → twentythree category list
```

Each command file exports a class extending `Command` from `@oclif/core` with static `flags`, `args`, and a `run()` method.

### Pattern 2: Generated Types, Handwritten Commands

**What:** `api/types.ts` is fully generated from the OpenAPI 3.1.0 spec via `openapi-typescript`. It is committed to source control and regenerated on spec updates. Commands are **handwritten** — they are the human-facing UX layer and should not be generated.

**Why:** Code-generating CLI commands from an API spec produces mechanical, poor-quality UX. Flags get wrong names, help text is raw API description text, terminology is wrong (photo vs video). The typed client layer gives you safety without sacrificing UX quality in the commands themselves.

**When:** Types regenerated via script when the API spec changes. Commands written once per resource, then maintained.

### Pattern 3: Middleware for Cross-Cutting Concerns

**What:** OAuth 1.0a signing, workspace context injection, and error normalization all live in openapi-fetch middleware. No command touches HTTP mechanics directly.

**Example:**
```typescript
// api/auth-middleware.ts
const authMiddleware: Middleware = {
  async onRequest({ request, options }) {
    const workspace = await getActiveWorkspace();
    const signed = oauthSign(request, workspace.credentials);
    request.headers.set('Authorization', signed.Authorization);
    return request;
  },
  async onResponse({ response }) {
    if (response.status === 401) {
      await triggerTokenRefresh();
      // signal retry
    }
    return response;
  }
};
```

### Pattern 4: Workspace-Scoped Client Factory

**What:** `api/client.ts` exports a factory function `createWorkspaceClient(workspaceId)` not a singleton. Each command call creates a client scoped to the active (or flag-overridden) workspace.

**Why:** Multi-workspace support requires the base URL to vary per workspace domain. A singleton with a fixed base URL breaks this. The client is cheap to instantiate (it wraps fetch); there is no connection pool to manage.

### Pattern 5: Agent-Friendly JSON Output

**What:** All commands accept a `--json` flag (built into oclif). Additionally, provide a `--agent` flag that emits a richer envelope:

```json
{
  "ok": true,
  "data": [...],
  "summary": "3 videos in workspace example.twentythree.com",
  "breadcrumbs": [
    "twentythree video get --id 123",
    "twentythree category list --video-id 123"
  ]
}
```

**Why:** The SKILL.md agent instruction document tells agents to use `--agent` mode for structured navigation. Breadcrumbs reduce the number of round-trips an agent needs to explore the API.

### Pattern 6: SKILL.md as Versioned Companion

**What:** `packages/skills/skills/twentythree/SKILL.md` is authored and maintained alongside the CLI. It is not auto-generated. It contains:
- YAML frontmatter with `name`, `description`, `trigger` patterns
- Agent invariants (what the agent must always do/never do)
- Quick reference table of every command with exact syntax
- Decision trees for common agent workflows
- Exit code reference

**Why:** The Basecamp pattern (verified in their `basecamp/skills` repo) shows a comprehensive, manually authored document dramatically outperforms auto-generated tool descriptions for agent use. The 155-endpoint Basecamp SKILL.md is structured human prose, not machine output.

## Anti-Patterns to Avoid

### Anti-Pattern 1: Code-Generating CLI Commands

**What:** Using `openapi-generator-cli` or similar to produce complete command implementations from the spec.

**Why bad:** API specs use legacy terminology (`photo`, `album`, `live`). Generated command flags mirror raw parameter names, not human-readable ones. Help text is API-spec description prose, which is often terse or incomplete. The generated code is hard to maintain — any spec update requires regenerating and then diffing against your customisations.

**Instead:** Generate only `api/types.ts` (type definitions). Write commands by hand using those types. This is a one-time investment per resource that pays off in UX quality.

### Anti-Pattern 2: Singleton API Client With Hardcoded Workspace

**What:** A module-level `const client = createClient({ baseUrl: process.env.API_URL })`.

**Why bad:** Multi-workspace is a first-class requirement. A singleton cannot switch workspace context between commands or within a single session.

**Instead:** Factory function `createWorkspaceClient(workspaceId)` called at the start of each command's `run()`.

### Anti-Pattern 3: Storing Tokens in Plain JSON Without Keychain Fallback

**What:** Writing bearer tokens directly to `~/.config/twentythree/credentials.json` as the primary mechanism.

**Why bad:** Plain JSON on disk is readable by any process running as the same user. On macOS and Windows, the OS keychain provides encrypted-at-rest storage for free.

**Instead:** `keytar` as primary store (OS keychain); JSON file as fallback when keytar is unavailable (CI, headless Linux). Never store the raw token in a plain-text file without this ordering.

### Anti-Pattern 4: Publishing CLI and Skills as One Package

**What:** Including SKILL.md files inside `twentythree-cli` and having agents consume them from `node_modules`.

**Why bad:** Agents that install skills need a lightweight package with no runtime dependencies. Bundling skills inside the CLI forces a 12MB+ install just to get markdown instruction files. Also breaks independent versioning.

**Instead:** Separate `twentythree-skills` package. Agents run `npx skills add twentythree-skills` (or equivalent skill installer). CLI releases trigger a parallel skills publish via Turborepo pipeline.

### Anti-Pattern 5: Imperative Token Refresh Blocking Commands

**What:** Checking token expiry at the start of every command and blocking until refresh completes before making any API call.

**Why bad:** Adds latency to every command invocation. Most tokens are valid; checking synchronously wastes time.

**Instead:** Background interval refresh during long-running sessions. For short-lived CLI invocations (the common case), refresh on 401 response via middleware retry. Only block if the token is already known-expired at call time.

## Monorepo vs Multi-Repo Decision

**Recommendation: pnpm workspaces monorepo (single repo, two packages).**

**Rationale:**
- Skills package content is version-coupled to the CLI — commands referenced in SKILL.md must match commands that exist in the CLI. A monorepo enforces this at the PR level.
- Turborepo release pipeline can publish both packages atomically: `cli` publishes first, `skills` publishes second with a reference to the same CLI version.
- Zero shared runtime code means no circular dependency risk.
- Shared TypeScript config, ESLint rules, and test setup reduce maintenance overhead.

**Multi-repo rejected because:** Skills content references CLI commands by name. Keeping them in sync across repos requires coordinating release PRs. The Basecamp reference implementation co-locates skills in the CLI repo (`basecamp/basecamp-cli` publishes to `basecamp/skills` on release).

## Build and Publish Pipeline

```
monorepo root (private, never published)
  |
  |-- turbo build
  |     |-- packages/cli: tsc → dist/
  |     |-- packages/skills: no build step (markdown only)
  |
  |-- turbo test
  |     |-- packages/cli: jest/vitest
  |
  |-- release (triggered by version tag)
        |-- packages/cli
        |     npm version + npm publish (twentythree-cli)
        |     postpublish: echo version into packages/skills/package.json
        |
        |-- packages/skills
              npm publish (twentythree-skills)
              (after cli publish succeeds)
```

**Tool choices:**
- `pnpm workspaces` — package management and workspace linking
- `turborepo` — task scheduling, caching, and build graph
- `changesets` — version management and changelogs (industry standard for monorepos)
- GitHub Actions — CI/CD; build → test → publish workflow

## Scalability Considerations

| Concern | At 20 commands | At 100+ commands | Notes |
|---------|---------------|-----------------|-------|
| Command load time | Instant | May be slow if eager-loading | oclif lazy-loads via manifest; regenerate manifest on build |
| Type compilation | Fast | May slow TypeScript LSP | Use `tsconfig` project references for `api/types.ts` as isolated package |
| Credential store lookup | O(1) | O(1) | keytar lookups are keyed by service+account |
| API client instantiation | Negligible | Negligible | openapi-fetch client is a thin wrapper, no connection pool |
| SKILL.md maintenance | Low | High | At 100+ commands, SKILL.md needs structure: quick-reference tables, decision trees |

## Recommended Build Order

The following sequence reflects hard dependencies. Each item must be completed before the next can be built reliably.

```
Phase 1 — Foundation (nothing else can start without this)
  1.1  Monorepo scaffold: pnpm workspaces + turborepo + tsconfig base
  1.2  config/paths.ts: XDG config directory resolution
  1.3  auth/store.ts: keychain + JSON fallback credential persistence
  1.4  api/types.ts: generate from OpenAPI spec; commit generated file

Phase 2 — API Client Layer (depends on 1.3, 1.4)
  2.1  api/client.ts: createWorkspaceClient() factory using openapi-fetch
  2.2  api/auth-middleware.ts: OAuth 1.0a signing via oauth-1.0a library
  2.3  api/term-map.ts: legacy→modern field name translation

Phase 3 — Auth Commands (depends on 2.1, 2.2, 1.3)
  3.1  auth/workspace.ts: workspace discovery via /api/2/user/tokens
  3.2  commands/auth/credentials.ts: the onboarding flow
  3.3  commands/auth/switch.ts: workspace switching
  3.4  auth/token-refresh.ts: background refresh

Phase 4 — Core API Commands (depends on 2.x, 3.x)
  4.1  commands/video/*: the primary resource (highest value to users)
  4.2  commands/category/*
  4.3  commands/webinar/*
  4.4  remaining resource topics — can be built in any order after 4.1

Phase 5 — Skills Package (depends on 4.x being stable)
  5.1  packages/skills/skills/twentythree/SKILL.md: author comprehensive agent doc
  5.2  packages/skills/package.json + publish pipeline
  5.3  Turborepo release task chaining CLI publish → skills publish
```

**Critical path:** `1.3 → 2.1 → 2.2 → 3.2` — the credential store feeding the auth middleware feeding the credentials command. This is the first working vertical slice.

## Key Technology Choices with Rationale

| Layer | Technology | Version | Rationale |
|-------|------------|---------|-----------|
| CLI framework | `@oclif/core` | v4 | First-class TypeScript, plugin/topic architecture, lazy command loading, `--json` flag built-in. Chosen over Commander (no built-in topics/plugins) and Yargs (no structured command files). 70-100ms startup overhead is acceptable for a developer tool. |
| Type generation | `openapi-typescript` | v7 | Generates TypeScript types from OpenAPI 3.1.0. The TwentyThree spec is confirmed 3.1.0. Lightweight (type-only, no runtime). |
| HTTP client | `openapi-fetch` | latest | 6kb typed wrapper using generated types. Per-request middleware for OAuth signing. No manual type assertions. |
| OAuth signing | `oauth-1.0a` | v2.2.6 | 610K weekly downloads; the de facto standard for OAuth 1.0a in Node.js. Crypto function is injected (uses Node's built-in `crypto`). |
| Credential storage | `keytar` | v7 | Native bindings to OS keychain on macOS/Windows/Linux. Async promise API. Falls back to JSON if unavailable. |
| Config paths | `xdg-basedir` | latest | Cross-platform `~/.config/` resolution per XDG spec. Sindre Sorhus maintained. |
| Interactive prompts | `@inquirer/prompts` | v7 | Successor to `inquirer`. Used for workspace selection during auth setup. |
| Monorepo | `pnpm workspaces` + `turborepo` | latest | pnpm for fast, disk-efficient installs. Turborepo for task graph and caching. |
| Versioning | `changesets` | v2 | Industry standard for monorepo changelog and publish automation. |
